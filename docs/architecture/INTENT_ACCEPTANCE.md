# Local Intent Acceptance Journal

Status: explicit Host SDK storage, not an enabled business workflow.

`IntentAcceptanceStore` adds durable local acceptance to the signed
[IntentEnvelope](INTENT_ENVELOPE.md) primitive. It does not start on import,
load an identity, grant capabilities, execute a solver, or create a
Task/Mission/Agreement. No REST route, UI, or automatic promotion is enabled.

## Atomic Boundary

The store lives under `.nth/intent_acceptance_v1/acceptance.sqlite3` inside the
explicit workspace. SQLite is part of the Python standard library; Ed25519
verification still requires the existing `nth-dao[crypto]` extra.

Acceptance separates expensive verification from the atomic write boundary:

1. Snapshot and verify the signed artifact before calling Host policy.
2. Capture all bounded journal rows in a short read transaction. Release the
   database transaction before verifying signatures, context and audit chains.
3. Start `BEGIN IMMEDIATE`, recheck the closed schema and compare **every stored
   field** with the verified snapshot. A changed snapshot is retried from a fresh
   read, at most four attempts, then fails with `IntentAcceptanceBusy`. A matching
   tail or row count alone is not sufficient. No persistent trust cache is used.
4. Call the trusted synchronous `resolve_context(head)` under the writer lock.
5. Read the trusted clock after that callback and check the full envelope
   against its returned `IntentAcceptanceContext`.
6. Return an exact existing artifact as `created=False`, or enforce the next
   revision, predecessor digest, unused nonce, capacity, and nondecreasing clock.
7. Insert the artifact, policy-context snapshot, nonce binding, and audit
   observation in the same row after a final clock/expiry check. Require exactly
   one inserted row and exact readback of all fields before committing with
   `synchronous=FULL`. A successful result is returned only after COMMIT succeeds.
   The recorded time is the final pre-insert observation, not a guarantee about
   the physical disk flush completing before expiry.

The revision head is keyed by `(audience_did, scope_id)`, **not signer**. A new
signer cannot silently reset an existing scope to revision 1. A scope identifies
one Host-defined revision stream; unrelated intents need distinct scope IDs.
Nonce uniqueness is keyed by `(audience_did, scope_id, signer_did, nonce)`.
Database uniqueness constraints back both invariants. SQL update/delete triggers
reject ordinary in-place history edits; the SDK exposes neither operation.

Version and application markers alone do not establish a valid database. The
table definition, unique indexes and trigger bodies must match the closed v1
schema. Missing, additional or changed schema objects fail closed, without
automatic repair. This includes manually added tables, indexes or triggers;
schema extensions need an explicit versioned migration. Whitespace-only DDL
formatting from the original v1 writer is accepted. INSERT readback is a second
guard against a silent ignored or rewritten write, not a substitute for schema
validation.

## Host Responsibilities

`resolve_context` receives only the persisted `IntentAcceptanceHead`, with
revision 0 and an empty digest at genesis. It must resolve expectations for the
explicitly reviewed operation from trusted local state, never copy wire fields
into authority. It is called again for exact retries. Returning `None`, a dict,
or a boolean is not approval. A denial, error, or invalid context commits nothing.

SQLite errors raised by this callback become the sanitized
`IntentAcceptancePolicyUnavailable`, not `IntentAcceptanceBusy` or
`IntentAcceptanceStoreError`. This distinction applies to both new acceptances
and exact retries. `PermissionError` and other non-SQLite Host exceptions retain
their original type. Journal lock, insert and COMMIT failures keep their storage
error classification. Callers must not infer acceptance from any failure.

Membership, role, delegation, revocation and key-rotation rules are **not
automatically integrated**. The Host must keep its policy source stable through
the transaction, for example by holding its own policy lock around `accept()`.
The store cannot atomically lock a separate governance database or membership
file. This integration must exist before a remotely accessible acceptance or
promotion endpoint is enabled. The callback must not perform network I/O or
reenter the store; long callbacks still hold the writer lock. The configured
`timeout` bounds SQLite lock waits, not callback execution or total operation
time. Four snapshot attempts are a retry-count limit, not a wall-clock deadline.

No key is loaded or generated by the store. All signatures are supplied by the
caller and verified. The persisted context records a local observation, not
independent proof that the Host applied correct governance or obtained human
consent. Signed draft constraints are still text, not an executable policy.

## Reads and Recovery

- `accept(envelope, resolve_context=...)` returns an immutable
  `IntentAcceptanceResult(record, created)`. Exact live retries do not append or
  rewrite audit history. `created=False` is not permission to rerun any action.
- `get(envelope_digest)` returns a verified historical record or `None`.
- `history(after_sequence=0, limit=100)` returns a bounded tuple of records;
  its JSON-valued properties return detached views.
- `verify_history(expected_tail_digest=...)` validates all envelopes, historical
  context checks, nonce uniqueness, scope revisions, sequence continuity, audit
  links and timestamps. It returns `(record_count, audit_tail_digest)`.

Empty genesis returns `(0, "")`. Passing `expected_tail_digest=""` requires an
empty captured journal; it rejects a journal with any record. `None` means no
expected-tail check. Thus a retained tail can be passed back unchanged, including
before the first acceptance. Read methods return a verified point-in-time
snapshot; a concurrent append after capture need not appear in that result.
They release their read transaction before doing cryptographic verification.

Expired requests cannot be accepted again, even as retries. Historical reads
verify against the stored acceptance time, so a caller can recover the original
receipt-like observation after expiry without manufacturing fresh authorization.
If a commit outcome is uncertain, reopen and query the exact envelope digest
before deciding whether to retry. Never infer rollback just from an I/O error.

Recovery tests cover a child exit after INSERT but before COMMIT, a real SQLite
COMMIT blocked by another connection's read transaction, and a child exit after
successful commit but before delivering its response. The first two leave no
accepted record or consumed nonce; the last is recovered by digest lookup and
an exact retry without another append. These are process/transaction tests,
not a power-loss or storage-device durability certification. Other tests cover
simultaneous first-open, competing revisions, policy denial, schema drift,
snapshot tampering, bounded churn and concurrent retries at the default capacity.

## Audit and Storage Limits

`record.audit` is a hash-linked local `intent.accepted` observation with the
signed envelope digest, context digest, sequence and acceptance time. It carries
`authority=none`, `commit_authority=false` and `executable=false`. It is **not a
signed Spine event**. No Spine event type is registered and no dual-write bridge
is enabled. A durable, idempotent Spine bridge remains a separate step.

A local hash chain is not tamper-proof against a workspace owner who rewrites
the database and its hashes. Retaining an audit tail outside the database lets
`verify_history(expected_tail_digest=...)` detect truncation or replacement.
No automatic deletion, pruning, repair, or reset is performed on corrupt state.

The default limits are 1,024 records and 16 MiB of envelope/context JSON bytes.
Configured limits cannot exceed 4,096 records or 64 MiB. SQLite overhead and
journals are additional disk usage, not covered by this logical payload limit.
Before full rows cross into Python, SQL scalar aggregates check every stored
field's type and byte/integer bounds, plus total record and JSON byte limits.
Text lengths are measured as BLOB bytes, so embedded NULs and multibyte text
cannot bypass these bounds. Metadata has separate per-field limits; it is not
part of the JSON quota. Corrupt oversized metadata is rejected before Python
materializes it. This does not impose a native SQLite memory or physical file
size limit, both of which remain Host operational responsibilities.

Every operation currently verifies complete bounded history: O(n), deliberately
without a trust cache. Moving that work outside SQLite transactions avoids
holding locks for the cryptographic scan, but does not remove its CPU cost.
Short capture/comparison transactions still copy bounded rows; temporary memory
can contain more than one snapshot. The 1,024-record, approximately 13.7 MiB
capacity test checks both concurrent retries succeed and reports elapsed times,
without asserting a hardware-dependent latency target. This is a modest local
review journal, not a low-latency global market index. Capacity exhaustion needs
explicit operational planning, not removal of nonce history. Physical quotas
and confidential-input retention remain Host responsibilities.

The database and drafts are not encrypted. Use a private, owner-controlled local
workspace with appropriate OS permissions. Link/reparse checks cover the path
and SQLite sidecars but are not a sandbox against local directory replacement.
Use a supported local filesystem, not a network share or a concurrently synced
SQLite file. Signed envelopes can be exchanged independently; merging local
acceptance heads or importing remote authority is not implemented here.
